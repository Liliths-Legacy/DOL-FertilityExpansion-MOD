# 1.5.15 侧栏加载提示调查（2026-10-09）

后续已发布本地 1.5.16 修复包，普通模块独立执行及验证结果见 [发布验证记录](0.5.12-release-validation.md)。下文保留修复前的调查结论。

## 结论与边界

已从本地 DoL 0.5.12.13 / ModLoader 2.101.1 的实际源码及浏览器复现确认：伊甸园普通脚本仍与其他模组共用一个执行单元，前置脚本抛出异常会使伊甸园全部普通模块无法初始化，而独立早期模块保持可用。这能够精确产生反馈截图中的七项功能缺失。1.5.15 提前加载孩子资料并增加保护，但没有隔离其余普通模块。

这是已证实的失败机制和本模组的加载薄弱点，不等于已确定反馈者的第一条异常来自哪个模组。无法取得对方整合包、完整模组版本与运行环境，不能排除普通脚本被其他加载插件移除或改写等情况，也不能把任意加载日志错误直接当作原因。无需孩子存档即可复现。

## 源码调用链

源码取自本地游戏 HTML 内嵌 webpack 模块，未依赖不同版本的在线仓库。

1. `ModZipReader.refillCacheScriptFileItems()` 按 `scriptFileList` 读取普通脚本，记录 `name = scPath`、`id = 0`。缺少文件时另有明确日志。
2. `SC2DataManager.patchModToGame()` 按模组顺序合并缓存。同路径的普通脚本通过 `concatMerge` 拼接；不是每个模组独立执行，也不是自动跳过早期脚本加载成功的模组。
3. `SC2DataManager.makeScriptNode()` 将非零编号的原版脚本排在前面；编号为零的模组脚本保持相对顺序。所有普通脚本拼成单个 `twine-user-script` 节点，文件之间只有注释头与换行。
4. SugarCube `Story.init()` 对整个 `tw-user-script-0` 调用一次 `Scripting.evalJavaScript()`，在外层捕获异常并报告。没有文件级捕获、重试或从下一模组继续执行。之后仍可以加载 widget，因此侧栏能执行保护提示。
5. `scriptFileList_inject_early` 经 `do_initModInjectEarlyLoadInDomScript()` 逐文件插入普通 DOM script，早于上述执行阶段。伊甸园孩子资料、运行检查、生产桥接、恢复和迁移模块属于这一类。
6. `edenSetup` 发现 `EdenRuntime.missing()` 非空后停止处理。反馈中的七项功能均为普通模块；连普通脚本中最前面的 `eden-adult.js` 也未通过检查。

单独审查 `eden-adult.js`：顶层主要建立常量、函数和导出对象，初始化不读取孩子存档，也不在导出前调用成长模块。其余普通模块正常拼接执行的测试通过，没有发现可以在已验证环境下自行导致七项功能全部缺失的初始化错误。

## 真正的 ModLoader 浏览器复现

使用仅本机服务、独立临时 Chrome 配置及未修改的 1.5.15 安装包。临时测试模组只有一个普通脚本，抛出标记异常 `Eden audit: preceding ordinary script failed`。没有读入或改写用户存档。

| 顺序 | 结果 |
| --- | --- |
| 测试异常模组 → 伊甸园 | 原版脚本已运行；伊甸园脚本仍存在于最终节点和 SugarCube 脚本列表，但成年模块未导出；早期模块可用；缺失列表为成长、天生属性、培养、孕期、成年结算、通讯录、人生来信。实际渲染 `edenSetup` 得到与截图相同的 1.5.15 提示。 |
| 伊甸园 → 同一个测试异常模组 | 仍捕获到同一个测试异常，但伊甸园缺失列表为空，`edenSetup` 正常执行。 |

因此移除/重装同一个包并不能保证解决问题。把伊甸园放到错误脚本之前，可以规避这一种中断，但不会修复其他模组自己的异常。侧栏现有“移除旧版或重复包”的提示过于单一，不能据此判断反馈者确实重复安装。

新增 `tests/eden-modloader-loading.test.js` 从实际 HTML 提取 `makeScriptNode()` 与 `evalJavaScript()`，验证同样的顺序对照及完整七项缺失列表；另验证 `console.error()` 本身不会中断后续初始化。与原有加载测试一起运行共 6 项通过，无跳过。

## 截图日志与本地组合核对

- `ModOrderContainer.getByNameOne()` 和 `getByNameOneWithAlias()` 找不到名字时记录错误并返回 `undefined`，自身不抛出异常。调用者后续是否错误使用返回值是另一个问题。
- `DependenceChecker.checkGameVersion()` 不匹配时记录错误、设置 `allOk = false` 并返回布尔值，不会在此直接抛错。游戏版本检查在游戏加载后执行。
- `TweeReplacer` 的 `cannot find findString` 是段落替换失败，不能直接证明发生了上述共享脚本异常。
- 本地伊甸园单独启动、PCBakery 0.3.4 在其前面、原版优化 1.1.0.1 在其前面，均观察到伊甸园全部检查通过。
- 清理临时配置中的启用缓存后，按 maplebirch 4.4.1 → 原版优化 1.1.0.1 → PCBakery 0.3.4 → 伊甸园加载，也得到空缺失列表。后续确实记录了 PCBakery 的游戏版本不匹配，但未阻止伊甸园注册。
- 本地框架是 4.4.1，反馈截图显示 5.3.3；DoLSims 与对方完整整合包不在本次测试中。这些对照不能为对方版本和组合排除冲突，也不代表旧面包坊玩法兼容 0.5.12。

## 修复方向

彻底处理这个薄弱点需要隔离剩余模块的初始化，明确区分可以提前注册的纯数据功能与需要游戏/DOM 准备好的界面功能，验证原版函数作用域、事件注册时机及读档引用。不能只把全部文件随意改成早期脚本，也不能靠隐藏侧栏提示或跳过检查解决。当前调查未改动发布包及加载顺序，仍为 1.5.15。
